# Phase 0 Research: Complaint Routing to Refund Agent

This feature has one real technical question; everything else (LLM client, structured-output shape, graph wiring) was already resolved in `specs/001-router-agent/research.md` and is reused unchanged.

## 1. How to satisfy Test-First (Principle I) for a prompt-wording change when the LLM boundary is always mocked

**Decision**: Add assertions in `tests/unit/test_router_agent.py` that check `router_agent.SYSTEM_PROMPT` (the module-level string, imported directly) contains specific phrases/instructions covering: (a) a past-order complaint routes to `refund` without needing refund/money-back language, (b) a complaint combined with an explicit refund ask is a single `refund` case, not the mixed-signal/`unclear` case, and (c) a complaint unrelated to a past order does not route to `refund`. These assertions are written and confirmed failing against the current prompt text before `router_agent.py`'s `SYSTEM_PROMPT` is edited, then confirmed passing after — a genuine red/green cycle. Alongside these, mocked-`RouterDecision` plumbing tests (same pattern as the existing `test_refund_query_carries_negative_sentiment`) are added for the spec's acceptance scenarios, primarily as executable documentation and regression coverage of `router_agent()`'s state-shaping behavior, not as the change's correctness driver.

**Rationale**: Every existing router test (`tests/unit/test_router_agent.py`, `tests/integration/test_router_trajectory.py`) mocks `router_agent._build_llm` to return a pre-selected `RouterDecision`, so none of them can distinguish "the prompt correctly instructs the model" from "the prompt says nothing at all" — they only verify what `router_agent()` does with whatever decision it's given, which is unaffected by this feature. Since this project has no live-LLM eval harness (confirmed: no such test exists anywhere in `tests/`, and `001-router-agent`'s "90% accuracy" test also mocks the decision it expects), the only artifact that can genuinely fail before this feature is implemented and pass after is the prompt text itself. Asserting on its content is the minimal way to give Principle I's red-green requirement real teeth for this kind of change, without inventing new test infrastructure (Principle III).

**Alternatives considered**: A live-LLM integration test that sends real complaint-style messages through `router_agent()` against the actual OpenRouter-backed model and asserts on the returned destination — rejected as out of scope for this feature: it would require new test infrastructure (network access, API key handling, flakiness tolerance/retries, cost) that no existing feature in this codebase has, and is a bigger change than a prompt-wording fix warrants (Principle III). It remains a reasonable future addition if the project later adopts a live-eval harness, but nothing in this feature's spec requires it. Skipping any new test and relying solely on manual review of the prompt diff — rejected because it violates Principle I outright (no failing-then-passing test would exist for the change). Adding a code-level heuristic (e.g., keyword matching for "cold", "late", "missing", "wrong") as a fallback/override on top of the LLM classification instead of a prompt change — rejected as materially more complexity (a second classification mechanism running alongside the LLM call, with its own false-positive/negative surface) for a problem the existing single structured-output call is already positioned to solve once correctly instructed (Principle III).
